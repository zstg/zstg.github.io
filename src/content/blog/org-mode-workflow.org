There is a version of this post that used to argue the opposite, so it is worth
saying plainly: I now write everything in Org-mode and convert it to Markdown at
build time. This is that pipeline.

* Why Org, for writing specifically

Org-mode is the only outlining tool that lets me move a layer of a document
around without breaking the prose around it, and /refiling/ plus /archive/ mean
the drafting surface and the editing surface are the same surface.

For blog writing in particular:

- headline levels survive a convert, so the post's structure is real
- source blocks keep their language and get highlighted as Markdown fences
- babel blocks can run during drafting, and then be removed on export
- the file is one plain-text format, so it diffs sensibly

* The pipeline

The site no longer stores Markdown. Posts live in =src/content/blog/foo.org=,
and an Astro integration converts each one with pandoc during build:

#+BEGIN_SRC text
astro build
  -> integrations/orgmode.ts
       parse #+TITLE / #+DATE / #+FILETAGS ...
       pandoc -f org -t gfm --wrap=none --shift-heading-level-by=1
       write foo.md next to foo.org
  -> content collection loads foo.md
#+END_SRC

The Markdown is a build artefact and is git-ignored. What is committed, and what
I edit, is Org and only Org.

* Frontmatter mapping

The Org keyword header maps onto the collection schema:

| keyword      | field  |
|--------------+--------|
| #+TITLE      | title  |
| #+DATE       | date   |
| #+FILETAGS   | tags   |
| #+SERIES     | series |
| #+LANG       | lang   |
| #+TOOT       | toot   |

An unrecognised keyword is ignored rather than failing the build, so the header
can carry notes to myself that the site does not need.

* What does not survive

Some things need a light touch. Tables convert cleanly. Footnotes convert. Inline
~verbatim~ becomes code spans. But:

- Org macros do not exist in Markdown, so they must be expanded before export
- LaTeX fragments need the =--mathjax= flag if they are to render, which this
  site does not currently set
- custom image attributes survive only as Markdown attributes, which the renderer
  must be willing to pass through

None of these have mattered for prose, which is what most of a blog is.

* What I would do differently

Convert at request time rather than build time, if the answer to "how large does
the archive get" ever becomes "large enough to care about build speed".
